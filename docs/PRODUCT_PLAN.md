# 유튜브 시청 제한 크롬 확장 프로그램 기획안

## 1. 배경과 목표

**문제:** 유튜브 시청 시간이 과도해 업무·수면·집중력에 영향을 준다.

**제품 목표:** 사용자가 스스로 정한 규칙에 따라 지정 사이트(기본 유튜브) 접속·시청을 제한하고, **약속(commitment)이 쉽게 깨지지 않도록** 잠금·차단 UX를 둔다.

**원칙:**

- **규칙 우선:** 한 번 적용된 제한은 의도적으로 “즉석에서 풀기” 어렵게 설계한다. (단, 크롬에서 확장 비활성화·삭제 등 OS/브라우저 수준의 우회는 기술적으로 막을 수 없음 → [8. 리스크](#8-리스크와-대응) 참고)
- **트리거 2종:** (1) **시간대 기반** — 특정 시간대에는 사용 차단 또는 허용만 (2) **누적 이용 기준** — 하루(또는 리셋 주기) 동안 일정 시간 사용 후 차단
- 두 트리거는 **AND/OR 조합**으로 설정 가능하게 하는 것을 목표로 한다. (예: “평일 09–18시에는 아예 차단” + “하루 총 60분 초과 시에도 차단”)
- **프라이버시:** 시청·집계 데이터는 서버로 보내지 않고 로컬에만 저장한다.

---

## 2. 타깃 사용자

- 특정 시간대에는 아예 보지 않거나, 하루 총 시청량을 엄격히 제한하고 싶은 사람
- “설정만 살짝 바꿔서” 우회하는 것을 스스로도 막고 싶어 **설정 변경 쿨다운**을 원하는 사람
- 유튜브 외에 **추가 사이트**에도 같은 규칙을 적용하고 싶은 사람

---

## 3. 핵심 기능

### 3.1 제한 조건 (트리거)

| 종류 | 설명 | 예시 |
|------|------|------|
| **시간대 제한** | 요일·시작·종료 시각으로 “차단 구간” 또는 “허용 구간” 정의 | 평일 22:00–익일 07:00 차단 |
| **누적 이용 제한** | 리셋 주기(기본 자정 등) 안에서 **집계된 사용 시간**이 한도에 도달하면 차단 | 하루 유튜브 합산 45분 초과 시 차단 |
| **조합** | 시간대 조건과 누적 조건을 동시에 사용 | “낮에는 30분만” + “밤 시간대 전면 차단” 등 |

**집계 기준(설정 가능):** 포그라운드 + 재생 중만 / 탭 열림 포함 등 — 구현 단계에서 옵션으로 둔다.

### 3.2 차단 사이트 목록

- 기본값: `youtube.com`, `youtu.be`(및 필요 시 모바일·서브도메인 패턴)
- 사용자가 **도메인 또는 URL 패턴을 추가**해 동일 규칙으로 차단·집계 대상에 포함
- 편집 UI는 옵션 페이지에서 목록 추가/삭제; **설정 잠금 규칙**(아래 3.4)이 적용되면 변경 불가

### 3.3 차단 시 동작

- **차단 활성 상태**에서는 해당 사이트에 대한 **정상 이용 불가**(오버레이, 네트워크 차단, 또는 리다이렉트 중 택일·병행 — 기술 검토)
- **차단이 걸린 동안에는 확장 UI에서 “차단 해제”“오늘만 예외” 등으로 막는 동작을 제공하지 않는다.**  
  해제는 **조건 만족 시에만** 자동 (예: 시간대 종료, 일일 리셋 후 한도 미만)
- “소프트 모드(5분 연장)” 등은 **본 제품 방향과 상충**하므로 기본 제외. (필요 시 향후 “초기 온보딩에서만 선택” 수준으로 재검토)

### 3.4 설정 잠금 · 약속(Commitment) 정책

| 규칙 | 설명 |
|------|------|
| **설정 변경 쿨다운 24시간** | **의미 있는 설정**(일일 한도, 시간대, 차단 사이트 목록, AND/OR 조합, 집계 방식 등)을 저장한 시점부터 **24시간 동안 동일 항목 수정 불가** |
| **표시** | 옵션 페이지·팝업에 “다음 설정 변경 가능 시각” 표시 |
| **차단 중 설정 변경** | 차단이 발동해 있는 동안은 **원칙적으로 설정 변경 UI 비활성 또는 숨김**(쿨다운과 별개로, “막힌 상태에서 규칙 바꿔서 풀기” 방지) |

**예외·안전장치(기획 선택지):**

- 최초 설치 직후 **한 번만** “시간 조정 없이 전체 초기화(공장 초기화)”를 허용할지 여부는 구현 시 결정. 사용자가 완전 잠금에 동의하는지 온보딩 문구로 명확히 한다.
- 확장 제거·크롬 설정에서 비활성화는 항상 가능함을 숨기지 않고 FAQ 수준에서 안내.

### 3.5 확장 아이콘 팝업(툴바 클릭 시)

- **유튜브(또는 “주 대상 사이트”) 사용 시간이 실시간으로 증가**하는 표시(초 또는 분·초)
- 오늘(또는 현재 리셋 주기) **누적 사용량**, **남은 한도**, **현재 차단 여부**, **다음 설정 변경 가능 시각** 표시
- 팝업은 짧은 주기로 스토리지/백그라운드와 동기화하거나 `chrome.storage.onChanged` 등으로 갱신해 “살아 있는” 카운터 느낌을 낸다.

### 3.6 옵션 페이지

- 시간대 규칙 편집, 일일 한도, 사이트 목록, 조합 방식, 리셋 시각, (필요 시) 확장 전체 on/off는 **쿨다운·차단 상태 정책과 정합**되게 제한
- 첫 실행 온보딩: 규칙 요약 + “24시간 내 설정 변경 불가”“차단 중에는 해제 불가” 동의 체크

## 4. 사용자 시나리오 (예시)

1. **야간 차단:** 매일 23:00–07:00는 목록 사이트 전면 차단. 그 외 시간에는 하루 40분까지만 시청 가능 → 한도 소진 시 즉시 차단, **당일 해제 버튼 없음**
2. **출근 시간:** 평일 09–12시는 “집중 모드”로 해당 사이트 전면 차단, 오후에는 누적 한도만 적용
3. **멀티 사이트:** 유튜브에 더해 넷플릭스 도메인을 목록에 추가해 동일 시간대·동일 일일 한도로 묶어 차단

## 5. 기술 방향 (크롬 확장)

- **Manifest V3**, `service_worker`에서 주기·알람(`chrome.alarms`)으로 시간대 전이·리셋 처리
- **콘텐츠 스크립트:** 목록 도메인별 주입, 재생/가시성 이벤트로 백그라운드에 사용 시간 누적 보고
- **`chrome.storage.local`:** 일일 누적치, 규칙, **마지막 설정 커밋 타임스탬프**(24h 잠금), 차단 상태 플래그
- **사용자 추가 도메인:** `declarativeNetRequest` 동적 규칙 또는 확장 로드 시 권한 범위 설계 — 스토어 정책·`optional_host_permissions` 등 검토
- **팝업 실시간:** 백그라운드가 최신 누적값 브로드캐스트 또는 팝업이 주기적 pull

---

## 6. UX·디자인 가이드

- 팝업: **실시간 카운터**가 시각적 중심(남은 시간 링/바 등은 선택)
- 차단 화면: 단정한 메시지(“지금은 집중/휴식 규칙이 적용 중입니다”), **해제 CTA 없음**, 조건이 풀릴 때만 자연 복구됨을 문구로 안내
- 설정 페이지: 잠긴 항목은 회색 처리 + “YYYY-MM-DD HH:MM 이후 수정 가능”

---

## 7. 측정·성공 기준 (개인 프로젝트 기준)

- 의도한 시간대·한도에서 **실제 차단이 발동**하고, 차단 중 우회용 토글이 없는지
- 팝업 수치가 **실제 누적과 지연 없이** 대체로 일치
- 24시간 잠금·차단 중 편집 제한이 오동작 없이 지켜짐

---

## 8. 리스크와 대응

| 리스크 | 대응 |
|--------|------|
| 크롬에서 확장 끄기·삭제로 우회 | 제품은 “의지 보조 도구”로 포지셔닝, 설명에 한계 명시 |
| 설정 잠금으로 본인이 조정 못 해 곤란 | 온보딩 경고, (선택) 최초 1회만 공장 초기화 |
| 사용자 추가 도메인이 악성/오타 | 패턴 검증, 적용 전 확인 문구 |
| Web Store 정책·광범위 호스트 권한 | 필요한 호스트만 최소화, `optional_permissions` 등 검토 |
| 완전 잠금 시 긴급 상황 | 정책상 “해제 버튼 없음”이면 대안은 브라우저 확장 관리로 한정됨을 문서·UI에 명시 |

## 10. 기획 충분성 · 추가로 정리할 것

**지금 문서만으로도** MVP 구현을 시작하기에 **기능·UX·기술 방향은 충분**하다. 개발 들어가기 전에 아래만 짧게 확정해 두면 이후 설계가 수월하다.

| 항목 | 왜 필요한지 |
|------|-------------|
| **트리거 AND/OR 정의** | “시간대 차단 AND 한도 초과”인지 “시간대만 / 한도만 각각 독립”인지 진리표를 한 줄로 고정 |
| **집계·리셋 시각** | 자정 = 로컬 타임존인지, 서머타임(DST) 전환 날짜 테스트 시나리오 |
| **차단 구현 방식** | DNR만 / 오버레이만 / 병행 시 우선순위(유튜브 SPA 특성 포함) |
| **사용자 추가 도메인** | 허용 입력 형식(호스트만 vs 와일드카드), 최대 개수, 잘못된 패턴 거절 규칙 |

## 11. 보안·프라이버시 (확장만 개발할 때 보강할 내용)

“우회 방지(확장 끄기 불가)”는 **불가**이고, 여기서 말하는 보안은 **악의적인 사이트·다른 확장과의 상호작용, 스토어 정책, 사용자 데이터 취급**에 가깝다.

### 11.1 권한·노출 범위

- **`host_permissions` / DNR**: 차단·집계에 **필요한 호스트만**. 사용자 정의 사이트는 **`optional_permissions`** 또는 “추가 시에만” 권한 요청 패턴 검토.
- **스토어 설명**: 각 권한이 왜 필요한지 한 줄씩 적어 두기(심사·사용자 신뢰).

### 11.2 코드·메시징

- **원격 코드 실행 금지:** Manifest V3·CWS 정책 준수. 외부 URL에서 스크립트를 불러와 실행하지 않기.
- **`chrome.runtime.onMessage`**: 메시지 발신자 검증(내부·신뢰 컨텍스트만 처리). 웹 페이지가 확장을 사칭해 조작하는 시나리오 배제.
- **콘텐츠 스크립트**: 페이지와의 `postMessage`가 필요하면 출처·형식 검증; 페이지 스크립트를 신뢰하지 않기.

### 11.3 UI·스토리지

- **옵션/팝업**에 사용자가 입력한 도메인·라벨을 그대로 HTML에 넣지 않기(필요 시 이스케이프, `textContent` 우선).
- **데이터:** 현재 기획대로 **서버 전송 없음**이면, 개인정보 처리방침에 “수집 없음·로컬 저장만”을 명시.

### 11.4 배포·운영

- **업데이트:** 스토어 배포본만 사용자에게 설치되도록(직접 배포 시 서명·무결성 안내).
- **GitHub 등 공개 시:** API 키·비밀번호 없음(본 확장은 원칙적으로 불필요).

구현 단계에서 위 항목을 체크리스트로 두고, 스토어 제출 직전에 **CWS 프로그램 정책·데이터 안전** 항목과 대조하면 된다.
